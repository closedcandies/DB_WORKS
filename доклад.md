
## Введение
Свойства **ACID** (Atomicity, Consistency, Isolation, Durability — Атомарность, Согласованность, Изолированность, Долговечность) - залог надежности и стабильности современного ПО. Эти четыре свойства, разработанные в конце 1970-х годов, гарантируют, что транзакции обрабатываются надежно, обеспечивая корректное состояние базы данных даже при сбоях системы или одновременном доступе.

PostgreSQL, как одна из самых продвинутых СУБД с открытым исходным кодом (по совместительству, моя любимая), полностью соответствует требованиям ACID, используя сложный механизм транзакций, многоверсионный контроль параллелизма (MVCC) и журналирование с опережающей записью (WAL) для обеспечения высокого уровня целостности данных.

Давайте же рассмотрим все парадигмы ACID, используя postgreSQL для примеров и поймем, насколько это круто.
## 1. Атомарность (Atomicity)
**Атомарность** гарантирует, что транзакция рассматривается как единая, неделимая единица работы. Это означает, что либо все операции в транзакции успешно завершаются (фиксируются), либо ни одна из них не применяется (откатывается). Частичные результаты транзакции невозможны.
### Реализация в PostgreSQL
PostgreSQL обеспечивает атомарность с помощью команд управления транзакциями: `BEGIN`, `COMMIT` и `ROLLBACK`. Если в ходе транзакции возникает ошибка (например, нарушение ограничения или сбой системы), СУБД автоматически выполняет откат, возвращая базу данных в состояние до начала транзакции.
### Пример PostgreSQL: Неудачный банковский перевод
Рассмотрим транзакцию по переводу 100 рублей с одного счета на другой. Предположим, что средства успешно были списаны со счета А, но при пополнении счета В объявили беспилотную опасность и отключили интернет.
```sql

BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE account_id = 'A';

-- Первая инструкция выполнена, но со второй возникли проблемы

-- пополнить счет В у нас не получится

UPDATE accounts SET balance = balance + 100 WHERE account_id = 'B';

-- После неудачной попытки выполнения инструкции выше Postgres

-- автоматически совершит ROLLBACK, вернув БД в исходное состояние

-- и предотвратив потерю средств на аккаунте А

COMMIT;

```

В результате отката, баланс счета 'A' остается неизменным, что предотвращает потерю средств и сохраняет целостность данных.
## 2. Согласованность (Consistency)
**Согласованность** гарантирует, что транзакция переводит базу данных из одного корректного состояния в другое. Это означает, что любая транзакция, которая начинается в корректном состоянии, должна завершиться в корректном состоянии, соблюдая все определенные правила, ограничения и бизнес-логику.

### Реализация в PostgreSQL
Согласованность обеспечивается на уровне схемы и данных с помощью:
- **Ограничений (Constraints)**: `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `UNIQUE`, `NOT NULL`.
- **Триггеров и Правил (Triggers and Rules)**: Для реализации более сложной бизнес-логики.
### Пример PostgreSQL: Нарушение ограничения CHECK
Предположим, в таблице `employees` есть ограничение `CHECK`, требующее, чтобы возраст сотрудника был не менее 18 лет.
```sql

CREATE TABLE employees (

id SERIAL PRIMARY KEY,

name VARCHAR(100) NOT NULL,

age INT CHECK (age >= 18)

);

  

BEGIN;

-- Валидная операция

INSERT INTO employees (name, age) VALUES ('Alice', 25);

  

-- Невалидная операция: нарушает ограничение CHECK

INSERT INTO employees (name, age) VALUES ('Sara', 16);

  

-- Вторая операция INSERT завершится ошибкой, и вся транзакция будет отменена,

-- не позволяя базе данных перейти в несогласованное состояние.

COMMIT;

```
Попытка вставить запись с возрастом 16 лет нарушит ограничение `CHECK`, что приведет к автоматическому откату всей транзакции (если не используется `SAVEPOINT`), сохраняя согласованность базы данных.

## 3. Изолированность (Isolation)
**Изолированность** гарантирует, что одновременное выполнение нескольких транзакций приводит к тому же результату, как если бы они выполнялись последовательно. Промежуточные, незафиксированные изменения одной транзакции не должны быть видны другим транзакциям.

### Реализация в PostgreSQL
PostgreSQL использует **Многоверсионный Контроль Параллелизма (MVCC)** для обеспечения изоляции. MVCC позволяет каждой транзакции работать с согласованным "снимком" (snapshot) базы данных, изолируя ее от изменений, вносимых другими параллельными транзакциями.

PostgreSQL поддерживает четыре уровня изоляции, определенных стандартом SQL (Давайте не будем рассматривать Read Uncommited - мир станет чуть лучше, если все про него забудут🥹):
1. **Read Committed** (по умолчанию): Транзакция видит только те данные, которые были зафиксированы до начала *каждой* команды.
2. **Repeatable Read**: Транзакция видит только те данные, которые были зафиксированы до начала *самой транзакции*. Это предотвращает неповторяемое чтение.
3. **Serializable**: Самый строгий уровень. Гарантирует, что транзакции выполняются так, как если бы они были единственными, работающими в системе, предотвращая все аномалии параллелизма, включая фантомное чтение.
### Пример PostgreSQL: Изоляция Repeatable Read
```sql

-- Транзакция 1

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

BEGIN;

SELECT balance FROM accounts WHERE account_id = 'A'; -- Читает баланс 500

-- ... Параллельно Транзакция 2 фиксирует изменение баланса на 600 ...

SELECT balance FROM accounts WHERE account_id = 'A'; -- Снова читает 500 (изолировано)

COMMIT;

```
В режиме `REPEATABLE READ` Транзакция 1 продолжает видеть исходное значение (500), несмотря на то, что другая транзакция (Транзакция 2) уже зафиксировала изменение (600). Это демонстрирует, как MVCC обеспечивает изоляцию, предоставляя каждой транзакции собственный снимок данных.
## 4. Долговечность (Durability)
**Долговечность** гарантирует, что после того, как транзакция была успешно зафиксирована (`COMMIT`), ее изменения сохраняются в базе данных навсегда и не будут потеряны даже в случае сбоя системы (например, отключения питания или аварийного завершения работы).

### Реализация в PostgreSQL
Долговечность в PostgreSQL обеспечивается в первую очередь с помощью **Журналирования с Опережающей Записью (Write-Ahead Logging, WAL)**.
- Перед тем как изменения данных будут записаны в основные файлы данных, они сначала записываются в журнал WAL.
- Команда `COMMIT` не возвращает управление клиенту, пока соответствующие записи WAL не будут гарантированно записаны на энергонезависимый носитель (диск).
- В случае сбоя, PostgreSQL использует записи WAL для восстановления всех зафиксированных транзакций, которые, возможно, еще не были записаны в основные файлы данных.
### Пример PostgreSQL: Фиксация транзакции
```sql

BEGIN;

INSERT INTO orders (order_id, product, amount) VALUES (1, 'Server', 1999.99);

COMMIT;

```
После выполнения `COMMIT` система гарантирует, что данные о новом заказе записаны в WAL и, следовательно, являются долговечными. Если сервер немедленно выйдет из строя, при перезапуске PostgreSQL восстановит эту операцию из WAL.

## Заключение
PostgreSQL является образцом СУБД, строго соблюдающей свойства ACID. Использование **MVCC** для изоляции, **WAL** для долговечности, а также строгая система **ограничений** и **транзакционных команд** для атомарности и согласованности, делает PostgreSQL надежным выбором для критически важных приложений, где целостность данных имеет первостепенное значение. Понимание и правильное использование этих механизмов позволяет разработчикам создавать отказоустойчивые и высокопроизводительные системы.
